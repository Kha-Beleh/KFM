# KFM

KFM запускается как обычное приложение в системе. В Docker работает только PostgreSQL.

## Запуск

Задайте `KFM_DB_PASSWORD` в файле `.env` и запустите БД:

```text
docker compose up -d db
```

В PowerShell:

```powershell
$env:KFM_DATABASE_URL='postgres://kfm:YOUR_PASSWORD@127.0.0.1:55432/kfm?sslmode=disable'
go build -o kfm.exe ./cmd/kfm
.\kfm.exe
```

В Linux:

```sh
export KFM_DATABASE_URL='postgres://kfm:YOUR_PASSWORD@127.0.0.1:55432/kfm?sslmode=disable'
go build -o kfm ./cmd/kfm
./kfm
```

В примере используется пароль без специальных символов URL. Для удалённой БД настройте TLS. Файл `.env` читает Compose; приложение получает настройки из переменных окружения.

## Пользователи и файлы

`register <login>` регистрирует пользователя, `login <login>` выполняет вход. Пароль вводится отдельно, в обычном терминале без отображения. `logout` завершает вход. Регистрация не выполняет автоматический вход.

Учётная запись KFM нужна для записи автора команды в журнал. Все вошедшие пользователи работают с обычными файлами системы в пределах прав той учётной записи ОС, которая запустила KFM. Дополнительных прав вход в KFM не даёт. Личные каталоги не создаются, `KFM_HOME` не используется, ограничения пользовательским корнем нет.

Текущий каталог при запуске определяется через `os.Getwd()`. `cd` меняет рабочий каталог KFM, `pwd` показывает его. Абсолютные пути, другие диски и относительные пути разрешаются по правилам ОС. Права на файл проверяет ОС.

`history` показывает последние 100 действий текущего пользователя. Журнал содержит команду, аргументы пути, время и результат, включая ошибки. Пароли и введённое содержимое файлов не записываются. Поле `owner_id` в метаданных связывает запись с действовавшим пользователем и не ограничивает доступ других пользователей к этому файлу.

## Команды

```text
help
register student
login student
ls [path]
cd [path]
pwd
drives
touch <path>
cat <path>
write <path> <n>
append <path> <n>
rm <path>
json-read <path>
json-write <path> <n>
xml-read <path>
xml-write <path> <n>
zip <source> <archive>
unzip <archive> <new-directory>
history
logout
exit
```

После команд записи вводятся `n` строк. Файл должен существовать; его можно создать через `touch`. При неполном или некорректном вводе запись не начинается. Поддерживается UTF-8, до 1 Мбайт на файл и до 10 Кбайт на вводимую строку. Запись добавляет LF после каждой строки. DTD в XML запрещены. Пути ZIP с пробелами заключайте в кавычки.

Ограничение каталогом назначения действует только при распаковке ZIP: архив не может писать за его пределами. Сам каталог назначения пользователь выбирает в любой доступной области ФС. Каталог должен быть новым. Лимиты ZIP: 1000 элементов, 10 Мбайт на файл, 20 Мбайт суммарно, 32 Мбайт на архив.

## Тесты

```text
go test ./...
go vet ./...
```

Интеграционные тесты требуют отдельной PostgreSQL с правом создавать схемы. Они используют временные схемы `kfm_test_*` и удаляют только их. Файловые проверки используют временные каталоги.

```powershell
$env:KFM_TEST_DATABASE_URL='postgres://kfm:YOUR_PASSWORD@127.0.0.1:55432/kfm?sslmode=disable'
go test -count=1 ./...
```

Без этой переменной интеграционные проверки явно пропускаются.

## Локальный CI/CD

Конвейер описан в `.github/workflows/main.yml`: `build -> test -> sast -> deploy`.
Задания выполняются в Linux-контейнерах. Для локального запуска нужны Docker
с работающим Linux-движком и `act`. В Windows используется Docker Desktop.

В PowerShell из корня репозитория:

```powershell
pwsh -File ci/run.ps1
pwsh -File ci/run.ps1 -Deploy
```

Первый вариант выполняет сборку, тесты и SAST. Второй дополнительно собирает
образ, запускает временную PostgreSQL и проверяет KFM в контейнере.
При отсутствии `KFM_CI_DB_PASSWORD` скрипт создаёт случайное значение только
в окружении своего процесса. Пароль содержит 12–72 латинские буквы и цифры,
чтобы его можно было безопасно включить в строку подключения.

В Linux запуск с уже заданным `KFM_CI_DB_PASSWORD`:

```sh
act workflow_dispatch -P ubuntu-22.04=ghcr.io/catthehacker/ubuntu:act-22.04 --input deploy=true --secret KFM_CI_DB_PASSWORD --env-file ci/act.env --secret-file ci/act.env --artifact-server-path .artifacts --cache-server-path .act-cache
```

В GitHub пароль задаётся как Actions Secret `KFM_CI_DB_PASSWORD`.
Пустой `ci/act.env` исключает автоматическое чтение обычных `.env` и `.secrets`
при локальном запуске: передаётся только явно указанный секрет CI.
Push и pull request запускают проверки без развёртывания. Развёртывание
включается вручную через `workflow_dispatch` с параметром `deploy=true`.
Не передавайте секреты непроверенному коду сторонних pull request.

Этап `build` выполняет `go mod verify`, `go vet` и собирает статический
Linux/amd64-бинарник с версией Go из `go.mod`. Артефакт `kfm-linux` содержит
бинарник и SHA-256. Кэш Go-модулей и компиляции восстанавливается через
`actions/setup-go`, ключ зависит от `go.sum`.

Этап `test` запускает `go test -count=1 -json -coverprofile=... ./...`.
PostgreSQL для интеграционных тестов создаётся отдельно. Пропущенные тесты
считаются ошибкой CI. Штатные команды `go tool cover -func` и
`go tool cover -html` создают сводку и HTML покрытия. Это отчёт покрытия,
а не JUnit и не HTML со списком всех тестов. Подробные результаты находятся
в `tests.json`. Артефакт `test-reports` сохраняется и при ошибках.

Этап `sast` использует готовый образ `semgrep/semgrep:1.186.0`, сохранённый набор правил `p/golang`
в `ci/semgrep-go.json` и дополнительный запрет запуска оболочки.
Снимок правил получен с `https://semgrep.dev/c/p/golang` 21.11.2026;
метаданные и условия лицензии правил сохранены в JSON.
Проверяются 12 файлов приложения в `cmd` и `internal`.
Файлы `*_test.go` исключаются стандартными правилами Semgrep.
High, Critical и старое обозначение Error блокируют конвейер; Low и Medium
сохраняются в отчёте. Ошибка сканера тоже блокирует выполнение.
Контрольный пример во временном каталоге проверяет срабатывание запрета;
его код не выполняется и не включается в KFM.

Этап `deploy` получает проверенный бинарник через артефакт и сверяет SHA-256.
Dockerfile использует две стадии: проверку и подготовку бинарника, затем
минимальный финальный образ с пользователем `10001:10001`.
`compose.ci.yaml` запускает отдельную временную БД. Проверяются регистрация,
вход, запись и чтение файла, а также три успешные записи аудита в БД.
Контейнеры, сеть и временные данные удаляются при завершении этапа.
Параметр `--rm` в `.actrc` также удаляет контейнеры заданий после ошибки workflow.
Собранный образ остаётся локально; журналы сохраняются в `deploy-reports`.

KFM не предоставляет сетевой сервис, поэтому порт приложения не публикуется.
База CI доступна только внутри Docker-сети. Обычный `compose.yaml` и установка
KFM в систему сохраняются как отдельный способ использования.

В локальном запуске артефакты находятся в `.artifacts`, кэш — в `.act-cache`.
Они исключены из Git. В GitHub срок хранения артефактов — 7 дней;
локальные файлы `act` нужно удалять самостоятельно.
Для сборки образа задание `deploy` получает Docker-сокет: это даёт доступ
к Docker хоста, поэтому такой запуск предназначен для доверенного локального
кода или отдельного CI-окружения. Привилегированный DinD не используется.
